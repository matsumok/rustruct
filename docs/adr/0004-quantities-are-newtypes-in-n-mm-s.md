# 物理量は自作の newtype で持ち、内部は N・mm・s に揃える

`rustruct-types` に `Length`・`Stress`・`Force` などの物理量の newtype を自作する。中身は N・mm・s の系に正規化した `f64` とし、作るときと取り出すときに単位を名前で言う（`Stress::n_per_mm2(24.0)`、`.as_mm()`）。この系では質量の単位が t になるので、剛性 N/mm と質量 t から ω² = k/m が係数なしで求まる。入力と表示の単位は Tool・値ごとに自由に決め、内部の系とは切り離す。型は使う Tool が出てから、要る分だけ足す。

`uom` クレートも検討した。次元解析はコンパイル時に完全になるが、型が重く、エラーが読みにくく、依存と WASM のサイズが増える。2026-10-14 に 0.38 で試すと、kN/m³ に当たる量も単位も無く「力 ÷ 体積」の名前の無い型になり、次元違いの足し算の型エラーは typenum の型が何行も並んで読めなかった。計算式をレビューで読みやすく保つため、式の中では `f64` に落として書けるほうを選んだ。`f64` のまま単位系を規約で一本化する案は、守るのが人になるので退けた（2026-07 の試作では Tool ごとに単位の流儀が分かれた）。単位を型パラメータに持たせる案（`Length<M>`）は、Tool をまたいで値を渡すたびに変換が要るので退けた。

内部を SI の一貫した系（m・kg・s、力は N、応力は Pa）にする案とも比べた（2026-10-14）。精度も式の書き方も変わらず、差は保存 JSON とデバッガで見える数だけで、N・mm・s なら Fc が規準どおり 24 と見える。保存 JSON には内部の系の数がそのまま出る。最初の保存形式 v1 を出す一本の前に、この系でよいかをもう一度見直す。保存 JSON だけ単位を名前に含めた値（`fc_n_per_mm2` など）にして、内部の系と切り離す案もそのとき比べる。
