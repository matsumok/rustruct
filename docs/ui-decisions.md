## 見せる前の点検

画面に出るものを変えたら、本人に見せる前に `sh scripts/screenshot.sh`（スマホ 375・iPad 820・PC 1280、ライトとダーク）で撮り、下の各項を自分で見て直す。本人は UI をレビューしない。細かい崩れを一つずつ指示させると手戻りになる（2026-10-15、本人の頼み）。迷う所だけ、候補を撮り比べて聞く。各項の規則は README「表」「数」にある。

**折り返し**
- 見出し・ラベル・表のセルが、語の途中で切れていない（「せん断補／強」「付着（上／端／筋）」）。改行は `br` で、意味の切れ目に置く
- スマホ幅で表が1単位に収まる。収まらない表は、その表だけ横にスクロールする
- 入力を変えても、結果の表の列が動かない

**揃え**
- 数値の列は右揃えで、小数点の位置が縦に揃う（E の数も）
- 4桁以上の数に3桁ごとの「,」がある。範囲の外の数は E で書かれている
- 括弧書きを添える値（「215（*195）」）は、括弧の外の数値がほかの行の数値と揃う
- 2行の列見出しは、行どうしが左で揃い、まとまりが列の右に寄る。並ぶ1行の見出しは上下の中央
- 同じ区分が続く列（「長期 引張・圧縮」「長期 せん断補強」）は、またがる見出し（「長期」）にまとまっている

**言葉**
- 表の名前は、内容が分かる名前にする。規準の表を写すなら、その表の名前（「呼び名」ではなく「異形棒鋼の寸法、単位質量及び節の許容限度」）
- 注記は1つの事柄に1つの箇条。2つの事柄を `br` で1つの箇条に詰めない

**広げる**
- 決め事を部品に入れたら、同じ部品を使うほかのページも撮って、同じ点を見る（小数点の揃えを鉄筋に入れたとき、コンクリートの許容応力度も揃っていなかった）
- 新しく決めたことは、規則を README に、決定と理由を ADR に足す。見て直す所が増えたら、この点検の項目も足す

## エージェントの動き方

- 本人が一歩ずつ自分の手で進める方針。設計の会話では聞かれたことに答え、小さく提案する。実装の単位は Issue 1 つ（`CODING_STANDARDS.md`）
- デザインを提案する前に `docs/design/README.md`（デザインシステムの正本）と関わる ADR とこの文書を読み、提案が前の決め事とぶつかる所を先に示す（2026-10-14、読まずに勧めて組み直した。ADR site-0006）
- 画面を変えたら、見せる前に撮って「見せる前の点検」の各項を自分で見て直す
- 値は `docs/design/tokens.json` から取る。勝手な色や大きさを足さない
- 決まっている規則に反する提案はしない。反する必要があるなら、どの規則に反するかを明示して理由を添える
- 未決のことを勝手に決めない。候補を出して本人に選んでもらう
- デザインの提案は実在するサイトを参照して、言葉より見た目で示す
- 「導出できる値は保存しない」「不変条件は構造で守る」は UI の状態設計にも適用する
